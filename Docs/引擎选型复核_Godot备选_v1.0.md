# 引擎选型复核：Godot 备选适配性评估 v1.0

> **文档性质**：评估与建议，**不是决策**。本文不修改任何设计真源（真源表 / 情报规格 / GDD 正文），结论需经评审分诊（直接采纳 / 修改后采纳 / 暂缓）后再决定是否升 GDD v1.3。
> **复核对象**：P0-1「引擎锁定 Unity 6 LTS」（GDD §5.1，2026-09-10 拍板）。
> **评估时点**：2026-09-11。
> **术语说明**：本文按 **Godot Engine**（.NET/C# 版）评估。用户输入"gotdot"按笔误处理为 Godot；若实际指其他候选，请以本文结构重跑。

---

## 0. 判定口径（可证伪）

本次复核只回答一个问题：**Godot 4.7 (.NET) 是否适合承载本作**，不重开 UE5 讨论。判定用四条标准：

| # | 判定标准 | 通过条件 |
|---|---|---|
| J1 | 能否承载权威服务器 + 感知过滤（P0-4 / NET-02） | 有可用的 headless 服务端路径，且规则层能在服务端独立运行 |
| J2 | 能否承载设计真源要求的规则层（真源表全部 CD/公式/门控） | 规则层不被迫改写公式或降级语义 |
| J3 | 是否引入新的不可接受风险 | 发布面（平台/生态/人力）无本项目无法承担的缺口 |
| J4 | 迁移成本是否低于其收益 | 一次性迁移成本 + 长期持有成本 < 收益 |

**证伪条件（先写下来，避免事后解释）**：
- 若实测显示规则层已强耦合引擎（而非实测的"几乎零耦合"），则 J4 不通过 → 结论翻转为"不迁移"。
- 若设计后续明确同屏单位规模进入**数百以上**量级，则 §4 关于"DOTS 论证不成立"的结论失效，需重新纳入评估。
- 若主机（PS5 / Xbox）从"后续目标"升格为**首发或承诺目标**，则 J3 不通过 → 结论翻转为"不迁移"。

## 1. 事实基线：本工程对引擎的真实耦合度（实测）

以 2026-09-11 仓库状态实测，不使用估计值：

| 指标 | 实测值 |
|---|---|
| C# 源文件 | 45 个，合计 **2406 行** |
| asmdef 程序集 | 10 个（Foundation / Time / Units / Intel / Stratagems / AI / Battle / Game / Editor / Tests） |
| 测试文件 | 8 个（NUnit，EditMode 语义） |
| 出现 `UnityEngine` 字样的文件 | **2 个** |
| 其中真正依赖 UnityEngine 的文件 | **1 个** —— `Assets/Editor/ChinaBettleProjectSetup.cs`（`[InitializeOnLoad]` + 写 EditorBuildSettings） |
| 另一个（`Foundation/Time/BattleClock.cs`） | 仅注释中出现该词，实为纯逻辑 |

**决定性证据**：仓库内已存在 `.tmp-dotnet/ChinaBettle.Verify.csproj`（net8.0 + NUnit + `Microsoft.NET.Test.Sdk`），直接编译 `Foundation / Intel / Stratagems / AI / Tests` 五个目录，可在**不打开 Unity** 的前提下用 `dotnet test` 跑通全部 EditMode 同款用例。

**由此得到两条结论：**

1. **规则层 100% 引擎无关。** 当前 Unity 实际只承担三件事：工程壳、`.meta`/asmdef 组织方式、Editor 工具。设计真源里的每一条公式、CD、门控都不依赖任何引擎 API —— 这本身就是 asmdef 分层纪律（Foundation `noEngineReferences: true`）生效的证明。
2. **现在处于全生命周期中引擎可替换性最高的时刻，且这个窗口正在关闭。** 按 `AGENTS.md` 的规划，场景内 GameObject / Prefab / MonoBehaviour 接线、ScriptableObject 数据资产均属垂直切片迭代；UI、动画、Steam 集成随之接入。每接入一层，耦合面就扩大一层（见开头成本曲线）。

## 2. Godot 现状核对（2026-09）

| 项 | 现状 | 对本作的影响 |
|---|---|---|
| 版本线 | 4.6（2026-01-26：Jolt 成为新工程默认物理、Modern 编辑器主题、Windows 默认 D3D12）；**4.7（2026-06-18）**：HDR 输出、AreaLight3D、wasm64、新版 Asset Store；8 月已有补丁版本 | 版本活跃，非停滞项目；但快速迭代也意味着升级回归需要预算 |
| C# 运行时 | .NET 8 起 | **与本工程 `dotnet test` 的 net8.0 目标框架一致**，规则层可直接引用 |
| C# 平台支持 | 桌面 / 移动可用；**Web 导出对 C# 仍为实验性** | 本作无 Web 目标，不构成阻塞 |
| 主机导出 | 无第一方路径，需第三方（如 W4 Games）；C# 走主机更弱 | **本评估中最硬的一项劣势**，直接对应 J3 |
| 专用服务器 | `--headless` + "Export As Dedicated Server" 预设（4.2+）成熟；服务端需 .NET 运行时 | 对 J1 有利；但 PC 端服务器部署多一层 .NET 依赖 |
| 内置联机 | `MultiplayerAPI` + `ENetMultiplayerPeer` + RPC/authority 语义为引擎内置 | 对 J1 有利：Unity 侧反而需要三期前评估 Fusion / Netcode / 自研 |
| ECS / DOTS | **无对等物**（Unity 的 Burst / Collections / Mathematics 在 Godot 无对应） | 见 §4：本作实际不需要，故不构成实质扣分 |
| Steam 集成 | GodotSteam / Steamworks.NET 等第三方 | 可用但非第一方，属"可接受的额外工作量" |
| 授权 | MIT，无版税、无营收门槛、无遥测；条款不可单方变更 | 对 J3/J4 有利，是本方案最主要的战略收益 |
| 编辑器体感 | 秒级启动、脚本热重载（非完整状态保留） | 对"规则迭代 → 测试锁定"的当前工作流有实质加速 |

**读法**：Godot 的劣势全部集中在**发布面**（主机、生态、招聘、中文资源），优势集中在**工程体感与条款**。规则层——也就是本作真正的设计资产——两边完全打平。这是本次评估最重要的一条结构性事实。

## 4. 关键发现：P0-1 的「ECS/DOTS」论证在本作不成立

GDD §5.1 选择 Unity 的理由原文是：**"ECS/DOTS 支撑 RTS 大量单位，团队 C# 积累可直接复用"**。

但按本作自己的数值口径：

- COMBAT-13 定：**1 个单位 = 100 人/队**；
- 情报规格 §4.1 的首个完整算例：赵军 **2000 兵 → 20 个单位**。

也就是说，本作是**指挥层级的兵力规模**（数十单位量级），而不是万人同屏的传统 RTS。设计支柱是信息不对称与欺骗，不是堆兵平推（`AGENTS.md` 范围控制节已明确）。**DOTS 这条理由在本作没有载荷**——`Packages/manifest.json` 里的 `com.unity.burst / collections / mathematics` 目前也确实是空挂的前置依赖，代码中并未使用。

**影响（与换不换引擎无关）**：
1. P0-1 的决策记录存在**论证与设计不一致**——用了一个本作不需要的技术理由来支撑选择。这是文档纪律问题，建议单独修订。
2. 支撑 Unity 的**实际权重理由**应当补记为：主机第一方发布路径、生态与中文资源厚度、团队 C# 资产、Steamworks 集成成熟度、招聘面。这些理由本身是成立的、且更诚实。
3. 反过来说：如果拿走"DOTS 支撑大规模单位"这条理由，Godot 与 Unity 在本作的差距**比 §5.1 呈现的要小得多**。

**证伪条件**：若后续设计明确同屏单位数进入数百量级（例如新增大规模会战剧本、或放弃"1 单位 = 100 人"的抽象粒度），本条结论作废，DOTS 重新成为有效权重并需重估。

## 5. 迁移成本分解（假设现在切换到 Godot）

| 层 | 内容 | 成本 |
|---|---|---|
| 规则层 | Foundation / Intel / Stratagems / AI / Tests（纯 C#，2406 行中约 95%） | **≈ 0**：作为 Godot .NET 工程的编译引用；NUnit 用例已能在 `dotnet test` 下跑 |
| 程序集组织 | 10 个 asmdef → Godot 的 .csproj / 程序集定义 | 低（机械替换，但分层纪律需重述为 Godot 术语） |
| `.meta` 体系 | 现有 GUID = `md5(归一化相对路径)` 的生成器与全部 `.meta` | 作废，可删；Godot 用 `uid` 机制，无需人工维护 |
| Editor 工具 | `ChinaBettleProjectSetup.cs`（启动日志 + 自动挂场景） | 重写为 Godot EditorPlugin，或直接删（Godot 无 EditorBuildSettings 概念） |
| 场景 | `Assets/Scenes/MainScene.unity`（当前为空骨架） | 重建为 `.tscn`，**成本极低——因为里面还没有东西** |
| 工程配置 | `ProjectSettings/ProjectVersion.txt`、`ProjectSettings.asset`、`manifest.json` | 替换为 `project.godot`；LFS/`.gitignore` 改 Godot 模板 |
| 文档 | `AGENTS.md` 工程约定整节；GDD §5.1 / §5.3 / 附录 A 的 P0-1 记录 | 中（约 1 节 + 3 处） |
| 设计真源 | 真源表 / 情报规格 / 兵种表 | **零改动**——三份文档都不含引擎假设，这本身是架构健康的证据 |

**一次性成本结论**：由于当前引擎耦合面仅 1 个文件，**"现在搬"这个动作本身的成本是历史最低点**。
**但真正的成本在"搬完之后"**：主机第三方移植与认证、无 ECS 的长期天花板、Godot C# 生态与中文资料缺口、团队招募面收窄、以及 4.x 快速版本迭代带来的升级回归预算。这些是**持续支出**，不是一次性支出。

## 6. 风险对照

**迁移会消解的风险**
- Unity 授权/条款未来再次不利变动（含营收门槛、运行时费用类政策）——MIT 不可单方变更。
- 编辑器迭代摩擦（domain reload）对"改规则 → 跑测试 → 改数值"高频循环的拖累。
- 网络中间件选型不确定性（当前 Mirror 已弃用，Fusion / Netcode / 自研待评估）——Godot 内置联机可覆盖其中一部分。

**迁移会新增的风险**
- **主机（PS5 / Xbox）发布路径退化为第三方移植**，且 C# 走主机更弱。GDD 目标平台明写主机为后续目标 → 这是最需要正视的一条。
- 生态与中文资料缺口：水墨风格资源、中文排版/字体方案、成熟中间件的可选项都更少。
- 招聘与协作面收窄：Unity 简历池显著更大。
- 无 ECS 对等物：当前不需要，但**关闭了未来"大规模会战"这类设计扩展的技术选项**。
- 版本迭代风险：Godot 4.x 仍在快速演进，升级需要预留回归预算。
- 团队既有投入：Unity 6 LTS 编辑器已在 Windows 侧安装（`D:\Unity\Hub\Editor`）、许可证已激活、`.meta` 体系已建立。

## 7. 结论与建议

### 7.1 结论

**技术上：合适。** Godot 4.7 (.NET) 能完整承载本作的全部设计真源——因为本作的规则层是引擎无关的纯 C#，且 Godot 的目标框架（net8.0）与本工程现有 `dotnet test` 验证链一致。J1、J2 通过。

**战略上：有条件。** 卡点在 J3——主机发布路径、生态厚度、招聘面，以及 Godot C# 在主机上的弱势。本作是"PC/Steam 优先 + 主机后续"，所以这**不是致命项，但是需要明确定价的项**。

**时机上：现在是最便宜的时刻，但不必现在决定。** 由于耦合面极低，"推迟决定"的代价几乎为零，而"立即切换"的收益并不紧急。**用最小成本换取最大可逆性**是当前最优解。

### 7.2 建议（按推荐度排序）

**建议一（推荐）：维持 Unity 主选，现在不迁移，但把"引擎可替换性"升格为工程硬约束。**
- 已满足部分：Foundation 层 `noEngineReferences: true`（继续保持，并扩展到所有规则层）。
- 需新增部分：约定"引擎类型禁止越过适配层进入规则层"；上层保持薄适配；垂直切片阶段禁止把规则逻辑写进 MonoBehaviour。
- 需修订部分：GDD §5.1 补记 Unity 的**实际权重理由**（主机第一方路径 / 生态 / 团队 C# 资产 / Steamworks），并记录本次复核；`Packages/manifest.json` 中未被使用的 DOTS 前置依赖（burst / collections / mathematics）建议评估后清理，避免"依赖即承诺"的误读。

**建议二（触发式切换）：满足任一条件即启动切换评估。**
1. 主机（PS5 / Xbox）从"后续"降级为**可选或移除**——此时 J3 的主要扣分项消失；
2. Unity 授权/商业条款再次发生不利变动且团队无法接受；
3. 垂直切片暴露出 Unity 编辑迭代速度成为实际瓶颈（有度量，不是感觉）；
4. 设计明确不再需要大规模单位扩展（DOTS 选项彻底作废）。

**建议三（若要在切片前定案）：用两周对拍代替争论。**
两边各做一个最小对拍，同一份验收清单，用数据决策：

| # | 对拍验收项 | 通过标准 |
|---|---|---|
| 1 | headless 权威端跑通情报 Tick + 信任门控 | 服务端可无显示设备运行，规则层输出与单机一致 |
| 2 | 水墨风格地图 + 中文文本渲染 | 达到可演示质量，字体方案落定 |
| 3 | 20 单位战斗（士气/结阵/火区）稳定运行 | 目标帧率稳定，无物理抖动 |
| 4 | 存档 JSON + 编年史回放 | 与 GDD §5.4 一致 |
| 5 | Steam 集成打通（成就/云存档任一） | 可验证的端到端链路 |

**明确不推荐的两条**
- 为"MIT / 免费"立刻推倒重来：当前收益（条款风险消解）不抵发布面代价，且收益并不紧急。
- Unity 与 Godot 双轨并行维护：两套工程壳 + 两套测试宿主，维护成本会吃掉全部收益。

### 7.3 决策门

> **定案时点**：垂直切片完成（首个可玩战役跑通）后 1 周内复核一次。届时耦合面已从"1 个文件"上升到含场景/UI/数据资产，迁移成本曲线已爬升，**该时点的数据才是有效决策依据**。
